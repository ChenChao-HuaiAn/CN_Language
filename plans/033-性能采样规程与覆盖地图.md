# 第一部分 #1226：热点常态化采样

## 1. 定位：三个工具各管一段

| 问题 | 工具 | 产物 | 不做什么 |
|---|---|---|---|
| 端到端快了多少？ | `scripts/bench_self_host.py`（#367·M1/M2/M5/M6） | `target/bench/性能基线报告.md` | 不做函数级归因 |
| 生成代码/运行时快了多少？ | `scripts/bench_stdlib.py`（#367·b1~b8 双编译） | `target/bench/stdlib基线报告.md` | 不剖析编译器进程 |
| **热点在哪个函数？** | **`scripts/perf_sample.py`（#1226）** | `target/perf/采样报告.md` + 可选 JSON | 不判优、不设阈值、不替代上两者 |
| 语法/语义差分？ | `scripts/cnsmith_*.py`（fuzz 面） | 差分清单/覆盖率 | 不做性能剖析 |

关系一句话：**`bench_*` 回答“快慢”，`perf_sample` 回答“为什么快/慢”，cnsmith 回答“对不对”。**

## 2. 统一入口

```bash
# Linux 原生（perf 优先；无 PMU 自动降级 callgrind）
python scripts/perf_sample.py --target linux-x64 --load v2-build --runs 3

# 冷/热口径分开（缓存任务强制）
python scripts/perf_sample.py --target linux-x64 --load v2-build --cache cold --runs 3
python scripts/perf_sample.py --target linux-x64 --load v2-build --cache hot  --runs 3

# win 原生：无 PMU/valgrind，只有墙钟降级报告（不得宣称收益）
python scripts/perf_sample.py --target win-x64 --load v2-build --runs 3

# win 热点归因：WSL callgrind 代理（--proxy-compiler 必须是同源 linux-x64 ELF；
# 需在 WSL/独立 Linux 构建中编译，win 的 cn.exe 是 PE，valgrind 不能执行）
python scripts/perf_sample.py --target win-x64 --load v2-build \
    --proxy-compiler /mnt/c/Users/<you>/CN/wtXXXX/target/perf/cn-linux --runs 1

# 运行时/微基准：直接剖析被测可执行文件
python scripts/perf_sample.py --target linux-x64 --load exec \
    --exec target/bench/b4_JSON解析.host --runs 3

# 自测（固定小负载 + 解析 + 无 PMU 降级路径）
python scripts/perf_sample.py --selftest
```

### 2.1 参数契约

| 参数 | 含义 |
|---|---|
| `--target auto|win-x64|linux-x64|linux-arm64` | 目标平台；auto 按主机探测 |
| `--backend auto|perf|callgrind|none` | 采样后端；auto=perf 优先，无 PMU 降级 callgrind，都无则 none |
| `--load v2-build|exec` | v2 全树编译（默认）或运行指定可执行文件 |
| `--compiler` / `--proxy-compiler` | 宿主编译器 / win 热点代理的 linux-x64 ELF 编译器 |
| `--entry` / `--output` | v2 入口 / 产物路径（默认 `CN语言编译器v2/主.cn`、`target/perf/perf_load.*`） |
| `--exec` / `--arg` | exec 负载的可执行文件与参数（可重复；以 `-` 开头的参数用 `--arg=--version` 形式） |
| `--cache cold|hot|asis` | 冷=禁用 AST/程序缓存；热=先预热一轮；asis=原样 |
| `--runs N` | 采样轮数（默认 3；callgrind 每轮独立输出） |
| `--top N` | 热点条数（默认 20） |
| `--timeout` | 单命令超时秒（默认 3600；callgrind 全树可能很慢） |
| `--wsl-distro` | WSL 发行版（默认系统默认；也可用 `CN_WSL_DISTRO`） |
| `--report` / `--json` | 报告 / 机器可读结果路径 |

### 2.2 输出契约

报告固定包含：

1. 目标平台、后端、代理口径、负载、缓存口径、轮数、完整命令；
2. **指令数**：callgrind `Ir` 或 perf `instructions` 的样本表 + 中位（收益硬口径）；
3. **热点 Top-N**：函数、self%、inclusive%、self 指令数、文件；
4. 口径备注：inclusive 可 >100%、墙钟仅参考、冷热分离、不参与门禁；callgrind 同名多
   文件条目分列，perf 按符号聚合（同名不同 DSO 已合并）；
5. 冷/热报告附 `[AST 缓存]`/`[程序缓存]` 统计：冷态命中应为 0（证明禁用环境进入
   子进程），热态记录命中；未捕获时显式写“未捕获”；
6. `none` 后端时显式红字：**没有指令级采样器，不得宣称性能收益**。

退出码：`0` 成功；`2` 用法/环境；`3` 平台边界（如 x86 宿主强求 arm64 指令级）；
`4` 负载失败（编译/被测程序非零退出、perf 权限不足等）。

## 3. 后端与平台边界（诚实口径）

| 环境 | 后端 | 能得到什么 | 不能得到什么 |
|---|---|---|---|
| Linux x86_64 原生 | `perf stat` + `perf record/report` | 原生 instructions、函数 self/inclusive | — |
| Linux 无 PMU（容器/WSL2） | `callgrind`（自动降级） | 确定性 `Ir`、函数 self/inclusive | 原生指令数绝对值 |
| Windows 原生 | `none`（墙钟）/ `callgrind` 代理 | 墙钟；Linux 同源构建的函数级热点 | **win 指令数/收益结论** |
| Linux aarch64 真机 | `perf` | arm64 原生 instructions/热点 | — |
| x86_64 宿主 + qemu arm64 | 拒绝（退出码 3） | 只能另用墙钟/产物行数 | **不得宣称 arm64 指令数收益** |
| 任意交叉架构（含反向） | 显式 perf/callgrind/auto 退出码 3 | 仅 `--backend none` 墙钟 | 指令数/收益结论 |

**统一架构边界**：指令级后端要求「目标架构 == 宿主架构」。x86_64 宿主测 arm64、
arm64 宿主测 x86_64、显式 `--backend perf`/`--backend callgrind` 都退出码 3；只有
`--backend none` 允许跨架构墙钟（报告仍标“不得宣称收益”）。

边界理由：

- valgrind 不能执行 PE，Windows 原生二进制无法 callgrind；代理结果只回答“同源代码哪段热”，
  不是 win 平台证据；
- qemu-user 不提供 guest PMU；callgrind 也不支持 qemu-aarch64 guest。arm64 指令级归因必须在
  aarch64 真机（或原生 arm64 CI runner）跑；
- `perf record` 需要 `perf_event_paranoid` 允许；失败时报告退出码 4，不伪造热点。

## 4. 操作流程（与 plans/032 对齐）

单侧采样：

1. 固定构建/命令/cwd/环境；冷态清缓存，热态先预热；
2. `--runs 3` 起步；报告样本表 + 中位；
3. 若墙钟受扰，只看指令数；
4. A/B 两侧**交替**执行（A B A B A B），不要先跑完 A 再跑 B；
5. 把 top-N 与指令数中位写进提交信息（plans/032 §9 模板）。

**A/B 六次调用与聚合**（每次 `--runs 1`；若每次 `--runs 3` 则每侧 9 样本）：

```bash
for i in 1 2 3; do
  python scripts/perf_sample.py --target linux-x64 --load v2-build --runs 1 \
      --compiler /path/to/A/cn --report target/perf/A_$i.md
  python scripts/perf_sample.py --target linux-x64 --load v2-build --runs 1 \
      --compiler /path/to/B/cn --report target/perf/B_$i.md
done
```

聚合：A 组 3 个样本取中位、B 组 3 个样本取中位；禁止六个混算，禁止只报最快一次。
冷/热口径分别成组；热态报告必须带命中统计。

可用性先例：

- **#1143**：perf 自采定位 `memchr`/`memmove`/string 拷贝/malloc 家族 → 分桶索引后
  M1 59.4s→32.3s（-45.6%）；采样总量 60053→31131；
- **#1154**：DWARF 栈采样定位 `types::canonical`/`isInteger`/`splitTypeSuffix`/
  `isResultType`/`isOptionalType`/`SourceLocation`，三步分别 -1.39%/-1.74%/-2.52% 指令；
- **#1248**：perf 定位 peephole 子树 11.31%（`normalizeReg` 的 strlen 21.4%、
  `takeWidthPrefix` 4.7%）→ 子系统 329.4→178.4ms（-45.9%）。

## 5. 与 #367 基准设施的关系

- `bench_self_host` 的 M1/M2/M5 是**验收数字**；`perf_sample` 的指令数/热点是**归因数字**；
- M1 不强制清缓存：命中时是热态 M1，报告必须写冷/热；冷 M1 与热 M1 不得直接比较；
- 优化前后验收仍以 `bench_*` 的端到端数字 + `plans/032` 等价性为准；
- `perf_sample` 的 `--load v2-build` 命令与 M1 同构（`cn build v2/主.cn`），因此热点可直接
  映射到 M1 的时间去向；
- `bench_stdlib` 的 b1~b8 产物可用 `--load exec --exec target/bench/<用例>.<侧>` 直接剖析
  运行时热点（如 #1310 的 `strlen` 族）；
- `perf_sample` 不设阈值、不挂门禁，避免把采样噪声变成红灯。

- 不建 cron、不改 CI/部署、不写看板日报；夜间轨道需另立运维任务并获用户批准；

# 第二部分 #1291：性能采样覆盖地图

## 7. 先划清：perf 采样 ≠ cnsmith 差分采样

| 维度 | perf/callgrind 采样（本文） | cnsmith 差分采样（#840/#893/#1053/#1188/#1270） |
|---|---|---|
| 问题 | 编译器**时间花在哪** | 编译器**行为对不对** |
| 输入 | 固定负载（v2 全树/微基准） | 随机/矩阵生成的 CN 程序 |
| 观测 | 指令流/函数 self%/调用栈 | 宿主 vs v2 输出/诊断差异、崩溃、覆盖率 |
| 产物 | 热点表、指令数 | 差分清单、语法形态覆盖率 |
| 失败形态 | 热点误判、口径混用 | 误编译、静默放行、崩溃 |
| 能否互相替代 | 否 | 否 |

**两回事的机械判据**：cnsmith 的“覆盖率”统计的是**生成了哪些语法形态**，不是**执行了哪些编译器函数**；
perf 的“覆盖”统计的是**采样命中了哪些函数/指令**，不是**语言特性覆盖**。两者数字不可互相引用。

## 8. 证据基础与诚实边界

本地图的证据来自已归档的提交信息、`plans/1167` 的 perf 阶段表、#1154/#1143/#1248/#1279/
#1153/#1207/#1155/#1267 的实测记录。**注意 1167 是 Debug + AST 缓存全命中的暖缓存口径**
（140 模块全部命中），lexer/parser 在多数模块被绕过；冷缓存路径需单独采样。
另：**没有把原始 callgrind/perf 数据文件入库**，因此：

- 本图是**模块/相位级证据图**，不是“逐函数零命中清单”；
- “未照亮”= 在已归档证据中未见该模块/子面的函数级采样归因，不等于“绝对从未执行”；
- 要机械生成函数级零命中清单，需后续用 `perf_sample.py --json` 累积原始样本 + 调用图；
  本轮先把“下一步该采哪里”定下来。

### 9.1 读图结论

1. **语义/优化/窥孔是已被照亮的主战场**：A/B 级（按 §9 口径）证据集中在这里，
   和 1167 的阶段占比一致；
2. **parser 是最大的未照亮区，但原因不是“剩余百分比”**：1167 的采样是 **AST 缓存 140 模块全命中**
   的暖缓存口径，lexer/parser 对多数模块被整体绕过；因此该样本里 parser 是零执行/零照亮。
   1167 表列项相加约 82.4%，剩余约 17.6%（含阶段重叠，实际只会更多）是**未拆解**的其他路径，
   **不能全归给 parser**（parser 在该样本零执行，但其余路径也没有函数级拆解）。
   要照亮 parser，必须用 `--cache cold` 专门采样；
3. **代码生成的非窥孔面被“窥孔热”遮住**：peephole 9.51%/11.31% 有数据，非窥孔发射器只有阶段级
   16.61%，寄存器分配（#1212）完全未按函数/宽度拆；
4. **运行时基本只有墙钟**：#1310 的 strlen 是明确例证——它从基准耗时推断出来，不是 perf 采样；
5. **win/arm64 原生没有指令级覆盖**：代理/模拟不能替代平台证据，报告必须写边界。
