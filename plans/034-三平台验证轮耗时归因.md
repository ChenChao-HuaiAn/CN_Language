## 0. 结论摘要

1. **三平台耗时差异 90% 以上发生在 e2e 段，不在构建段。** 构建（宿主编译器）中位：
   win 30s / linux-x64 123s / arm64 157s；e2e 中位：win 3059s / linux-x64 1480s /
   arm64 542s。win 的「构建/链接慢」直觉**不成立**——win 构建是三平台最快的，慢的是
   e2e 里**每个用例都要重新起编译/链接/运行进程**。
2. **win 的慢=每例固定开销 ~27s（linux 0.8s、arm64 0.7s），差距 20~40 倍。**
   win 上普通用例 worker 纯耗时中位 27.4s（近轮 8.9~27.4s 随实例/并发波动），负测类
   （只编译不链接）0.9~2.0s（linux 0.6~0.8s，仅 2~3 倍）——放大发生在「链接+运行+
   文件系统/杀软扫描」段，不是单纯进程创建。79_v2/78_v2 两跳合计 2714s（40bc8b39 轮），
   是 win 轮的**下界**（e2e 墙钟 ≥ 79_v2 单例 1893s）。
3. **linux-x64 的 554~2218s 极差主因是执行机，不是平台。** 同一平台按执行机：
   home-wsl-1 总中位 904 / home-wsl-2 1590 / VM-0-12 2105 / home-ubuntu-1 3158；
   79_v2 单例中位 463~2306s（差 5 倍），构建并行度 4 vs 2 核。**把 linux-x64 当一个
   口径比较会得出错误结论**。
4. **linux 分片对总墙钟几乎没有收益**（分片轮总中位 1608 vs 单实例 1552），原因有二：
   ① 分片度 3 时普通用例只分到 1 片（1432 例 1493s），从实例跑完 78_v2 后**串行**再跑
   普通片，主实例跑完 79_v2 后**空等**（f890b3f2 轮 e2e 记录 1493s，真实墙钟多 847s）；
   ② 分片度大时 78_v2 被派给慢机（44aebcbd 轮 home-ubuntu-1 跑 1641s，别的机 204~472s）。
5. **arm64 单列，不可直接比较。** 近期轮按平台限制跳过 78_v2/79_v2（跳过 3 例），
   e2e 仅普通用例（sum 923s / jobs 2 ≈ 460s）；10-22~10-23 之前的旧轮曾原生跑 78/79
   （ec2db377 轮 79_v2 2874.7s、78_v2 665.2s，总 3821s）。arm64 分片轮（818s）反而比
   单实例（568s）慢，分片在该平台是负收益。

## 3. 归因链

### 3.1 共同骨架：e2e 决定一切

三平台步骤和均 ≈ 总秒（残差中位 1–3s，同步/清产物秒级），即
**总秒 ≈ 构建 + e2e + （win 特有：示例 verify/asm_width/cli_contract）**。
e2e 占比：win ≈100%、linux-x64 92%、arm64 74%（arm64 构建 157s 占 22%）。

### 3.2 win-x64：每例固定开销 27s 是根因，不是构建

- 构建 30s（三平台最快；`scripts/ci_build.py` 注释载 win 冷建 ~23s 量级 + sccache
  吸收 291 引入的清建成本）。
- e2e 单实例轮 3059–6697s。用例耗时和 10881–34788s ÷ jobs 6 ≈ 实际墙钟
  （有效并行度 4.2–5.2）。
- **普通用例中位 27.4s/例（近轮），负测类（只编译）0.9–2.0s**——同一进程模型下，
  「编译→汇编（ml64）→链接（link.exe）→运行 exe→读 stdout」整链在 win 上比 linux
  慢 20–40 倍，而「仅编译失败」只慢 2–3 倍。结论：**放大项是链接+执行+杀软/文件系统，
  不是进程创建本身**。
- 79_v2 单例 1893s（1571–2970）、78_v2 807s（701–1106）：两跳合计 ~2700s，构成 win
  轮的硬下界；普通用例与之并行，但 sum 更大（32074s），所以 e2e 由普通用例 sum 主导。
- 同机三实例差异巨大（win3 2739 vs win2 4819；同轮 01_hello 41.2s vs 8.3s）——
  与同机并发/Defender 实时扫描状态强相关（#1426 同机饱和教训的同族证据）。

### 3.3 linux-x86_64：机器核数 × 79_v2 单例 × 分片调度

- **按机分层**：home-wsl（4 核，79 单例 463–487s，总 904–1590s）vs
  VM-0-12（2 核，79 单例 1255s，总 2105s）vs home-ubuntu-1（79 单例 2306s，总 3158s）。
  用户观察的 554–2218s 区间 = 这三类机混在一起的分布。
- 单实例轮 e2e 1653s ≈ max(79 单例, 78 单例, 普通 sum÷jobs)。
- **分片收益被调度抵消**：分片轮总中位 1608 ≈ 单实例 1552。两个失效形态：
  ① **片数 3**（池只 1 个空闲从实例）：普通用例只有 1 片（1432 例 ≈ 1493s），从实例
  跑完 78_v2（1084s）后**串行**再跑普通片；主实例 79_v2（1343s）跑完后**空等收片**
  ——残差 847s 未计入 e2e（f890b3f2）；
  ② **片数 8–10**：普通片被切成 28–37s 的小片，快；但 78_v2 被派给 home-ubuntu-1
  跑 1641s（其他机 204–472s），单点慢机成为整轮瓶颈（44aebcbd）。
- 树锁等待：linux 侧 `带门禁锁跑` 只在 win 取 gate_lock（`ci_daemon.py:293`），
  linux 无机器锁等待；分片轮走本实例树锁（#1424）。**linux 的「等待」全部来自分片
  认领/收片调度，不是树锁。**
- ccache：linux 构建中位 123s；标记「无缓存」的 5 轮 302–310s（均为 2 核机）；
  #1299 的 ccache 自动探测代码已就绪但 runner 未重启部署（待用户批准）。

### 3.4 linux-arm64：跳过面 = 口径不同

- 近期轮跳过 78_v2/79_v2 与交叉模拟面（e2e明细.跳过=3），e2e 542s 仅为普通用例
  （1226 例 sum 923s ÷ jobs 2 ≈ 460s）+ 少量调度；M6 显示「未跑·平台限制」。
- **历史口径**：10-22~10-23 前 arm64 原生跑 78/79（ec2db377：总 3821s，79 2875s、
  78 665s，且 79 固定点不一致红）。近期 500s 量级与旧轮 3800s 不可混算。
- arm64 分片轮（818s）比单实例（568s）**更慢**：分片召唤/收片开销 ~140s，而普通用例
  在 2 核机上本已接近线性，分片无收益。

## 4. 口径陷阱（引用数据时必须成对说明）

1. **arm64 跳过 78/79**，与 win/linux 全量轮不同口径；且 arm64 存在 10-23 前后的口径
   分期（旧轮原生跑 78/79）。
2. **`e2e并行` 在分片形态下记 max(片秒)**，从片串行认领时低估真实墙钟：linux 最近 30
   轮中 2 轮残差 >100s（最大 847s；更早的 4a54f22c 残差 1276s）。引用「linux e2e
   1493s」时要加上残差才是真实耗时。
3. **win 兜底轮恒不分片**（`ci_daemon.py:717`：分片只对 `ci/预验-*` 生效），而 win
   近期 21/23 轮是 develop 兜底轮——win 的 3000–7500s 是「单实例全量」成本；历史 win
   预验分片轮仅 2282–2386s，恰好证明 win 普通用例交给 linux 从片可减半。
4. **79_v2 逐用例耗时只在 7 个 linux 轮上报**（旧 daemon），这 7 轮是慢机轮，中位
   1248s 不代表 linux 全样本（M6 全样本中位 535s）。
5. **同平台执行机差异 > 平台差异**（linux 904 vs 3158），比较必须带 runner 维度。

## 5. 优化建议（按预计收益排序）

### A. linux 分片：主实例收片期空转 + 普通片数不足（收益 600–900s/轮·25%~35%）

- **现状**：f890b3f2 型轮的真实 e2e 墙钟 = e2e 记录 1493s + 残差 847s = 2340s——从实例
  跑 78_v2（1084s）后**串行**再跑普通片（1493s），主实例跑完 79_v2（1343s）后空等。
  即「三块重活（79 / 78 / 普通全集）只落在 2 台机器上，且普通全集没拆」。
- **建议**（三条可独立落地，收益叠加）：
  ① 主实例跑完片 0 后「空闲即抢补」普通片（现只在片缺失/心跳超时时抢补）；
  ② 普通片数设下限（如 max(N−重型组数, 普通用例数÷400)），片数 3 时普通至少拆 2–3 片；
  ③ **片 0 与重型从片附带普通子集**：`run_e2e` 分片选取让 79_v2/78_v2 与普通用例同池
  并发（重型单例只占 1 个 worker，其余 worker 现全程空转）——这是收益最大的一条。
- **收益**：①② 可把 f890b3f2 型轮从 2340s 降到 ~1900–2100s（-10%~-19%）；叠加 ③ 后
  e2e 由 max(79 1343, 78 1084, 普通÷片数) 决定，约 1400–1500s（-36%~-40%），linux-x64
  分片轮总中位 1608 → ~1100–1300s。
- **风险**：主实例抢片与从实例并发需保证 CAS 不双跑（服务端 claim 已原子）；③ 让 79/78
  与普通用例并发时，run_e2e 的内存保护（--max-mem-mb / 重型单跑）与 #1426 同机饱和
  教训需保持；e2e 记录口径（max 片秒）应同步改为真实墙钟，否则收益不可观测。
- **改动面**：`scripts/ci_shard.py`（收片/抢补策略、召唤）、`tests/e2e/run_e2e.py`
  （分片选取），`scripts/ci_duration.py`（口径，可选）。门禁语义（e2e 全量跑完）不变。
- **需用户批准**：是（CI 分片语义变更）。

### B. win 每例固定开销（收益 30%~40%·约 1000–2500s/轮）

- **现状**：普通用例 27.4s/例，负测（只编译）0.9–2.0s；放大发生在链接+运行+杀软/文件
  系统。同机同轮 01_hello 41.2s vs 8.3s，波动极大。
- **建议**（按风险从低到高）：
  ① 部署项：Windows Defender 对 `target/`、e2e 工作目录、`ml64.exe/link.exe` 加排除
  （与 #1299 同类的 runner 部署面）；
  ② 观测项：`run_e2e` 为每用例增「编译/链接/运行」三段计时（现只有总耗时，无法分离
  杀软成本；见「遗留未知」）；
  ③ 评估项：win e2e `jobs=6` 是否匹配家机核数（三 win 实例同机 + WSL 实例共享 CPU，
  盲目加大 jobs 会复现 #1426 同机饱和）。
- **收益**：若 27.4s → 15s，e2e 6697 → ~3800s（-43%）；若仅 Defender 排除生效 20%
  （27.4→22s），e2e -18%。
- **风险**：Defender 排除属安全策略变更（需用户/运维批准）；jobs 调整可能加剧同机
  争抢。
- **改动面**：部署脚本/机器配置（A、B ②），可能 `tests/e2e/run_e2e.py`（③）。
- **需用户批准**：是（安全策略与 CI 部署）。

### C. linux ccache 部署（收益 90–280s/轮·6%~17%）

- **现状**：#1299 的 ccache/sccache 自动探测代码已就绪（`scripts/ci_build.py`），
  但 runner 未重启部署；构建中位 123s，2 核机「无缓存」轮 302–310s。
- **建议**：按 #1299 方案在 runner 部署 ccache 并重启 daemon（win 侧 sccache 先例：
  冷建吸收后 ~30s 量级）。
- **收益**：构建 123 → ~30s（-75%）；2 核机 308 → ~30s（-90%）；总轮 -90s
  （home-wsl）~ -280s（VM-0-12）。
- **风险**：缓存污染（#859 sccache 命中污染面教训）；命中率需用 ci_duration 的
  「缓存态」档验证。
- **改动面**：runner 部署 + 重启（无代码改动）。
- **需用户批准**：是（任务线索③明确「待用户批准重启 runner」）。

### 附加 D. arm64 关闭分片（收益 ~140s/轮·19%·零代码风险）

- arm64 分片轮 818s vs 单实例 568s；2 核机上分片只增加召唤/收片开销。
- 建议：arm64 实例设 `CN_SHARD_N=1`（或服务端不向 arm64 派片）。
- 收益 ~140s/轮；风险=无（分片是加速面，不是正确性面）；改动面=实例配置。
- 需用户批准：是（CI 配置变更）。
