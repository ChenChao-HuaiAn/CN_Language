## §〇 总则：CN-OS 与 CN 语言的关系

**CN-OS 是目标，CN 语言是手段。**

传统路径是「语言先定型，OS 迁就语言的能力边界」——本文档反其道而行：先按完美标准定义操作系统，OS 的每一层需求反推出语言/编译器的演进任务。具体机制：

```
OS 蓝图各子系统需求
    ↓ 反推
语言缺口清单（§四 A/B/C 三组）
    ↓ 立法（§2.3 审批流程，B 组全部待立法）
语言/编译器实现任务（挂 plans/021 队列，排班进 M8 线）
    ↓ 实现
OS 侧验收（§六 各阶段验收判据——语言特性以 OS 能力形式验收）
    ↺ 双向反哺：OS 开发中发现的新缺口再次进入循环
```

这条循环与编译器现有主线（v2 自举双目标：性能超过 C++、安全接近 Rust）**不冲突且互相成就**：内核恰恰是「性能不妥协+内存安全零容忍」要求最极端的场景——v2 双目标的终极考卷就是内核。

**CN 语言为什么天生能写内核**（四句话哲学与内核需求的对应，〔基准=019〕）：

| CN 语言哲学 | 内核开发中的意义 |
|---|---|
| ① 默认路径零规则（值语义深拷贝无别名） | 内核数据结构天然无共享可变状态→数据竞争结构性根除，锁纪律从「程序员自觉」变「语言强制」 |
| ② 显式放弃安全=显式获得性能（`转移()`） | 热路径零拷贝：IPC 消息所有权移交、页描述符流转，无深拷代价 |
| ③ 危险面收口（`不安全 函数`） | 真正摸硬件的代码（MMIO/汇编/页表操作）显式审计，内核危险面最小化、可枚举 |
| ④ 拷贝消除是编译器义务（LUE/转移/COW） | 性能不输手写 C——内核不接纳任何「安全税」 |
| （无 GC·确定性析构） | 内核可用性门槛：GC 语言（Java/Go/Python）永远写不了内核，CN 合格 |

## §一 定位与哲学

### 1.1 CN-OS 是什么

**CN-OS**：以 CN 语言全栈实现（内核+系统服务+运行时+应用框架，零 C/C++ 代码）的、语言级内存安全的、高性能混合内核的全场景操作系统。

- **内核名**：CN-Kernel（混合内核，详见 §二）
- **形态序列**（远期）：服务器/桌面（x86-64/PC）→ 移动/平板（ARM64）→ 物联网/嵌入式（RISC-V 32 位裁剪版，远期评估）
- **首发形态**：RISC-V 64 位 virt 虚拟机（QEMU），无真机依赖

### 1.2 三大操作系统优点吸收矩阵

| 吸收对象 | 吸收的优点 | 在 CN-OS 中的落点 |
|---|---|---|
| **Linux** | 热路径性能（调度/内存/IO 直通路） | L1 内核态热路径直通（§二划线判据）；syscall fast path；性能对拍锚（§六持续项） |
| Linux | POSIX 生态 | L6 POSIX 源级兼容层（§3.8） |
| Linux | 开源治理与稳定性工程 | §七开发指南（门禁/对拍/三机协同全部沿用） |
| **安卓** | HAL 硬件抽象层 | L3 设备管理服务+HAL 接口（§3.4 驱动模型） |
| 安卓 | 应用沙箱+权限模型（安装时声明/运行时授权） | §3.7 安全模型 |
| 安卓 | 应用框架（Ability/Stage 生命周期模型） | §3.9 应用框架 |
| **鸿蒙** | 混合内核与确定性时延（实时调度类） | §3.1 调度器（DEADLINE/RM 实时类） |
| 鸿蒙 | 分布式软总线（设备发现/认证/组网/跨设备调度） | L4 分布式层（§3.8→§3.6 重编号见正文） |
| 鸿蒙 | 一次开发多端部署 | CN 源码多 ISA 后端编译（§五）+Ability 多设备形态 |
| 鸿蒙 | 编译器-OS 协同（方舟路线） | §四 B 组执行域类型系统——CN 版做得更彻底（编译器与 OS 同源开发，可定制语言级静态检查） |

**不吸收的（明确排除）**：Linux 宏内核的驱动崩溃即全机崩溃；安卓的 Java/ART 应用层（CN 应用直接编译原生码，无虚拟机无 GC）；鸿蒙对 Linux 内核的兼容包袱。

### 1.3 CN 独有立身之本（与其他 OS 的本质差异）

1. **无 GC 的语言级内存安全内核**：C/C++ 内核的内存安全只能靠人（Linux 内核漏洞统计中内存破坏类常年占比最高）；Rust in kernel（Linux RFC/Redox）证明这条路可行。CN 的差异点：默认路径零规则（Rust 要求全员学所有权，CN 安全区代码不需要学任何新规则）+ 中文语法降低母语者门槛。
2. **编译器-OS 同源协同**（裁决④）：编译器团队与 OS 团队是同一拨人（同一仓库同一纪律），OS 可以要求编译器提供别的语言给不了的静态检查——首例即执行域类型系统（§四 B-1：中断上下文调用睡眠函数=编译错误）。这是 C/Rust 都没有的（Rust 编译器团队与内核团队分离，红ox 也没做执行域静态化）。
3. **分层安全四条在内核态实例化**（plans/001 §1.1a）：编译期能证明的编译期拦（常量下标越界在内核构建时即报错）/证不了的安全区确定性失败兜底（页分配失败→错误码+受控panic，不静默 corruption）/完备访问通道并行提供/`不安全 函数`真零运行期检查。
4. **全栈同语言**：引导→内核→驱动→服务→框架→应用全部 CN，从上到下一套错误处理纪律（`结果<_,错误>` 强制检查贯穿 syscall 到驱动），调试链路统一。

### 1.4 命名

操作系统名 **CN-OS**、内核名 **CN-Kernel**、原生产物名前缀 `CNOS-`。均为工作名，用户可随时更名（登记于本节，全库引用统一替换）。

### 2.2 各层职责与构成

| 层 | 职责一句话 | 主要构成 | 崩溃影响 |
|---|---|---|---|
| L0 | 把内核装进内存并交权 | OpenSBI（RISC-V M 态固件，提供 SBI 调用）；设备树（硬件拓扑描述） | 无法启动 |
| L1 | 资源核心管理 | 调度器/内存/IPC 快路径/中断/时钟/capability 基座（§3.1~3.3） | 全机（故只放「小而精+CN 安全代码」） |
| L2 | 高频内核态服务 | VFS 元数据快路径、syscall 分发、capability 缓存校验 | 全机（同 L1，量小） |
| L3 | 易出故障的复杂服务 | 驱动/FS/网络/HAL/电源/显示——**全部服务化，崩溃自动重启** | 单服务重启，系统无恙 |
| L4 | 跨设备协同 | 软总线、分布式数据、跨设备调度 | 降级为单机 |
| L5 | 应用运行的土壤 | CN 运行时（libc 层+容器+IO）、货舱 OS 包管理、权限中心、Ability 运行时 | 应用级 |
| L6 | 让 Linux 世界搬得进来 | POSIX 兼容层、图形栈（合成器客户端库）、Shell/工具集 | 应用级 |

### 2.3 划线判据（什么进内核态，什么放用户态）

混合内核的质量取决于划线。CN-OS 的判据（按序检查，全部满足才进内核态）：

1. **纳秒敏感的热路径**：每次 syscall/缺页/中断都要走的代码（调度、页表操作、IPC 快路径）。
2. **崩溃不可恢复**：代码崩溃后系统无法自举恢复的底层设施（中断控制器、时钟初始化）。
3. **体量可控**：能被完整审计（CN `不安全 函数` 枚举+评审），万行级以内。
4. **无第三方代码**：只放 CN-OS 自研代码——所有硬件厂商驱动一律 L3 服务化（学安卓 HAL：厂商代码质量不可控，全部隔离在用户态）。

反之满足任一条即放 L3：复杂协议栈（网络/文件系统）、可降级服务（显示/电源）、生命周期需独立管理的实体（驱动实例）。

> **历史教训对照**：Linux 全家福进内核→驱动 bug 占内核崩溃大头；纯微内核全部外放→IPC 性能税。CN-OS 的答案：热路径进、故障面出，并用 `转移()` IPC（§3.3）把「出」的性能损失补回来。

## §三 关键子系统设计

### 3.1 调度器（吸收：Linux CFS + 鸿蒙确定性时延）

**设计目标**：普通负载吞吐不输 Linux；实时负载提供有界时延保证（鸿蒙卖点）。

**核心机制**：
- **SMP**：per-CPU 运行队列，工作窃取（idle CPU 从忙 CPU 队列尾偷任务）。
- **调度类分层**（学 Linux 调度类架构，简化为两类）：
  - `停止类`（DEADLINE/RM）：用户经 syscall 声明截止时间/周期，调度器准入检查后保证（EDF 最早截止优先）；拒绝准入返回 `错误` 而非静默降级（分层安全③完备通道）。
  - `公平类`（CFS 同构）：虚拟运行时间红黑树，权重=nice 值。
- **tickless**（无固定时钟滴答，CPU 空闲时完全静止，省电+减少无谓唤醒）。
- **QoS 等级**：应用可声明能效偏好（性能优先/均衡/省电），调度器据此选核（大核/小核，ARM64 后补时生效）。

**CN 语言关联**：任务控制块（TCB）为值语义结构体，队列间迁移用 `转移()`（任务在 CPU 间漂移=所有权移交，无别名）；运行队列锁粒度小（无共享可变数据 → §3.2 内存节）。

**验收要点**：sched_latency 微基准 vs Linux 对拍（§六持续项）；实时任务截止命中率 100% 负载测试。

### 3.2 内存管理（吸收：Linux 伙伴系统/slab/per-CPU）

**设计目标**：物理页分配 O(1) 级、内核堆无碎片、页表操作安全。

**核心机制**：
- **物理页管理**：伙伴系统（buddy，按 2^n 页阶分配合并）+ per-CPU 页缓存（单页高频分配免锁）。
- **内核堆**：slab 对象缓存（按类型尺寸分池，如 TCB/页描述符/IPC 消息各有专属池）——**设计复用 CN 编译器 v2 的 arena 经验**（plans/013：一次性批量分配+整数索引代替指针，cache 友好且天然安全——CN 内核堆优先 arena 化，slab 兜底异尺寸场景）。
- **虚拟内存**：RISC-V Sv39 页表（三级，后补 Sv48）；缺页处理在内核态快路径完成（匿名页/文件页映射），COW 缺页（fork/分布式数据共享的基石，§3.8）。
- **用户态内存隔离**：进程地址空间独立页表；capability 授权的跨进程映射（§3.7）。
- **CN 特色——无别名内核数据**：值语义深拷贝默认无别名 → 内核数据结构并发约束极简（多读者免锁直读的场景远多于 C 内核），RCU 风格只读共享（写时复制链表/树，旧版本延迟回收）作为读取热路径手段。

**CN 语言关联**：`物理地址/虚拟地址` 新类型（§四 B-3）防混用（C 内核经典 bug：两种地址都是整数，混用即灾难）；页表操作收口 `不安全 函数`；`易失` 指针（§四 B-2）访问页表基址等 MMIO 寄存器。

### 3.3 IPC 子系统（CN 最大亮点：`转移()` 语义的 OS 级应用）

**设计目标**：服务化架构（L3 一切皆服务）的主动脉——消息传递既要安全又要快到用户无感。

**核心机制——消息三档**：
1. **小消息（≤128 字节）：值拷贝直传**。CN 值语义天然形态：消息结构体整个复制进接收方，发送后发送方的副本自动失效（LUE/转移）。零共享、零竞争、路径可预测。
2. **大消息：`转移()` 所有权移交，零拷贝**。发送方 `转移(缓冲区)`，内核只交换所有权令牌（页描述符移交），数据一字节不动；发送方旧名禁用（编译器强制）→ 双释放/用后即焚结构性根除。**这一档直接补齐混合内核相对宏内核的 IPC 性能差距**（C 语言做不到安全零拷贝移交，要么整拷、要么裸共享内存赌命）。
3. **超大块/双向流：共享内存**，但必须经 `不安全 函数` 显式声明+capability 双方授权（危险面收口）。

- **capability 寻址**（学 seL4）：进程不持有全局命名（无 pid 直达），持能力令牌通信——令牌=「我可以向服务 X 发消息」的凭证，可授权/转移/吊销。IPC 目的地即能力，权限检查在令牌里不在路径上。
- **fast path**：同核热路径 vDSO 风格优化（高频只读 syscall 经用户态映射页直答，免陷入）；异步消息队列（发送方不阻塞等接收方）。
- **服务注册/发现**：系统服务管理器（L3）维护「服务名→能力」目录，服务崩溃重启后能力自动迁移到新实例（对客户端透明）。

**接口草案**：

### 3.4 驱动模型（吸收：安卓 HAL + 鸿蒙 HDF）

**设计目标**：驱动=用户态服务，崩溃可重启；一套驱动框架跨 ISA。

**核心机制**：
- **用户态驱动服务**：每个驱动（或驱动组）是 L3 服务。DMA/中断注册等特权操作经「内核驱动代理」接口申请（capability 授权），代理校验后代执行。
- **HDF 式分层**（学鸿蒙驱动框架）：平台层（总线：virtio/USB/PCIe）→ 设备层（块设备/网卡/输入）→ 业务层。设备树声明式绑定（设备树节点→驱动服务名），无硬编码。
- **热插拔**：设备树变更事件→设备管理服务动态启停驱动服务。
- **崩溃恢复**：驱动服务心跳+看门狗；崩溃→设备管理服务重启之→队列中请求重放或如实报错（分层安全②确定性失败，不静默吞）。

**CN 语言关联**：MMIO 寄存器访问=`易失` 指针+`不安全 函数`（寄存器读写不可被优化消除——C 的 volatile 语义，CN 收口进危险区）；DMA 缓冲区所有权经 `转移()` 移交；设备协议状态机用 CN `枚举`+`选择` 表达。

**验收要点**：QEMU virtio-blk/net 驱动跑通；**驱动注入崩溃（人为 kill 驱动服务）→系统不死机→服务重启→IO 恢复**（阶段 4 演示项，服务化架构的招牌演示）。

### 3.5 文件系统（吸收：Linux VFS 设计 + 日志式 FS 工程实践）

**核心机制**：
- **内核 VFS 快路径**（L2）：路径解析缓存、dcache 同构、元数据操作直通；真正的 FS 逻辑在 L3 文件系统服务。
- **CNFS 原生文件系统**：日志式（journal 先行，崩溃后可重放）；B+ 树目录；小文件 inline 存储；**值语义友好布局**（文件元数据结构体定长，slab 池分配）。
- **兼容挂载**：ext4/FAT32 只读（生态过渡期读 U 盘/Linux 盘）；写支持远期评估。
- **页缓存**：内核态统一页缓存（file→page 映射），`转移()` 档页移交给用户（零拷贝 read）。

**验收要点**：QEMU virtio-blk 上建/读/写/删；断电模拟（QEMU 强杀）后日志重放一致性；IO 吞吐 vs Linux ext4 对拍。

### 3.6 分布式子系统（吸收：鸿蒙软总线）

> 注：蓝图规划期编号为 §3.6（原计划文档中为 §3.8，落盘时按章节顺序整理）。

**核心机制**：
- **软总线**：设备发现（局域网 mDNS 式+蓝牙扫描，远期）→认证（设备身份+capability 授权）→组网（虚拟总线，屏蔽传输差异）。
- **分布式数据**：跨设备对象共享——**COW 容器（plans/021 任务 099）的 OS 级验收场**：本地容器副本零拷贝共享，首写分离，版本向量合并。语言任务与 OS 任务在此闭环。
- **分布式任务调度**：应用 Ability 可声明「可迁移」，运行态（栈+数据）经 `转移()` 序列化漂移到另一设备（鸿蒙超级终端体验）。
- **硬件能力共享**：远端设备的摄像头/屏幕/麦克风经 capability 代理为本地可用。

**验收要点**：双 QEMU 实例软总线组网；一个 Ability 从实例 A 迁移到 B 继续运行；分布式数据一致性（并发写合并正确性）。

### 3.7 安全模型（吸收：安卓权限 + seL4 capability + 分层安全四条）

**核心机制**：
- **capability 基座**：一切资源访问持令牌（IPC 通道/文件/设备/内存区）。无令牌=无访问，无全局命名空间可枚举（最小权限的结构性保证，学 seL4）。
- **应用沙箱**：安装时声明所需能力清单（学安卓 manifest）→安装器呈现用户批准→运行时逐能力可吊销（比安卓更细：安卓吊销即重装，CN-OS 吊销即失效）。
- **分层安全四条内核实例化**：①编译期拦（内核构建时常量越界/除零即红——继承编译器能力）；②运行期确定性失败（空指针→错误码+受控 panic，内核态 panic 策略=§四 B-5）；③结果化 API 全覆盖（syscall 一律 `结果<T,错误码>`，无 errno 全局状态）；④`不安全 函数` 真零运行期检查（热路径）。
- **TEE 远期**：TrustZone（ARM64 后补期）或 Keystone（RISC-V）承载可信应用，登记远期不排班。

**验收要点**：无授权访问被拒的全覆盖负测；权限吊销即时生效实测；syscall 层错误处理强制检查（编译器保证，抽查）。

### 3.8 POSIX 源级兼容层（裁决③）

**核心机制**：
- **L6 用户态库**：CN 实现的 POSIX 接口子集（文件 open/read/write/close、进程 spawn/exec、socket、pthread 最小集、errno 映射），静态链入应用。鸿蒙 musl 层同构思路。
- **映射原则**：POSIX 返回码（-1+errno）↔ CN `结果<_,错误码>` 在兼容层边界一次性翻译，内部全 CN 纪律。`fork` 这类与值语义哲学冲突的接口以 `_spawn`（显式传资源）替代并提供 `fork` 兼容包装（代价：内部全页 COW，正好是任务 099 验收场）。
- **目标软件画像**（首批移植验证集）：busybox 核心工具、Lua 解释器、zlib——覆盖「工具+解释器+库」三种形态即证明通用移植路径。
- **不做的**：Linux ELF 二进制直跑（黑暗区+绕过安全模型，与立身之本冲突；远期若生态压力极大，作为独立可选子系统单独立项呈报，默认不建）。

**验收要点**：上述三件移植件编译运行通过；POSIX 测试套（如 PJT 风格子集）通过率报告。

### 3.9 应用框架与图形栈（吸收：安卓 Ability/Stage；远期）

- **应用=Ability 集合**（学安卓/鸿蒙）：页面型（FA）/后台型（SA）Ability，生命周期由框架调度（创建/前台/后台/销毁）。
- **Stage 模型**：应用声明能力需求+资源配额，框架按 Stage 加载（学鸿蒙）。
- **包格式**：货舱生态延伸（`货舱.toml` 增 [应用] 节：能力声明/图标/入口 Ability）。
- **图形栈（远期，阶段 8）**：L3 显示合成服务（DRI 式：应用渲染到共享缓冲，合成器合成上屏）+GPU 用户态驱动+声明式 UI 框架（CN DSL）。本节仅立位不展开，阶段 6 启动时出专项设计卷。

### 4.2 B 组：OS 新增提案（登记待立法·本蓝图首提）

**B-1 执行域类型系统**（裁决④·超越 Rust 的旗舰提案）
```
内核态 函数 切换页表(新表: 物理地址) -> 无        # 只能内核态调用
中断态 函数 时钟滴答处理(上下文: 中断帧) -> 无    # 中断上下文专用域
可能阻塞 函数 接收消息(通道) -> 结果<消息,错误码>  # 标注会睡眠

规则：中断态函数内禁止调用「可能阻塞」函数——编译期错误 E-域冲突
     （C/Rust 无此静态检查；Linux 只能靠文档+评审+撞了才知道）
```
【提案示意·未立法·不可编译】
实施分两步：先只做「标注+跨域调用检查」（内核态/用户态/中断态三域），再做「可能阻塞」传播分析。收益：死锁类 bug（中断里睡眠）在编译期根除——内核最凶险 bug 类别之一的结构性消除。

**B-2 `易失` 指针**：MMIO 访问不被优化消除/重排（C volatile 对位）。收口进 `不安全 函数`（易失解引用=危险操作，进 023 清单）。

**B-3 `物理地址/虚拟地址` 新类型**：两个不透明整数包装类型，混用/直接算术（除页对齐屏蔽外）编译期拒绝。C 内核经典灾难的静态根除。

**B-4 `@对齐(N)/@节("名")` 属性**：页对齐静态数据（初始页表/内核栈）；自定义段（启动段/设备树段）。

**B-5 内核 panic 策略编译选项**：`--内核panic=停止/记录重启`——分层安全②的内核态变体（致命错→受控停机并留现场，而非 exit）。

**B-6 零运行时确认构建**：freestanding 目标下链接产物自检：无 CRT 符号/无宿主 IO 依赖断言（构建期机器检查，防止运行时依赖漏进内核）。

**B-7（远期提案）内核静态分析 pass**：锁序图死锁检测、capability 流分析——编译器 OS 专属 pass，阶段 4 后评估。

## §七 开发指南

### 7.1 工程纪律（全部沿用现有体系）

- **零妥协纪律**（尽善尽美）：内核缺陷零容忍呈报流程照旧（现象/根因/影响面+≥3 方案含推荐）。
- **单一职责**：内核源码同样 ≤1000 行/文件、≤100 行/函数，超限拆子模块。
- **中文注释/中文提交**：内核代码同规。
- **模块单向依赖**：内核内部分层依赖也单向（L1←L2←L3 服务接口），禁反向。
- **新增语法规范须审批**：§四 B 组每一项落地前立法审批，不得以「内核需要」绕过。

### 7.2 测试策略（双测铁律 OS 化）

- **宿主单测面**：内核纯逻辑（调度器算法/伙伴系统/日志重放）以宿主单测覆盖——CN 值语义代码无副作用依赖，天然可宿主测试。
- **QEMU 集成面**：每功能=真内核镜像真 QEMU 启动真串口/磁盘/网络断言（防虚假验收：禁 mock 硬件，QEMU 即真目标环境）。
- **双面同源**：同一测试逻辑宿主与内核双跑对拍（算法层结果一致）——双测铁律的 OS 形态。
- **E2E 先行**：每阶段先写验收用例（`.expected` 串口输出/退出码），实现向用例收敛。
- **测试文件不可擅改**：照旧。

### 7.3 三机协同与云 CI

- OS 开发照走三机协议（分支即开发/队列即集成/异步验收）；任务线六要素落盘 025 照旧。
- TX_02 云 CI 加 qemu-system 包，`裸机.txt` 用例族进云全量；性能对拍锚脚本化。
- 内核构建产物（ELF/镜像）落 `target/`（gitignore），不散落。

## 附录 A 术语表（小白友好）

| 术语 | 通俗解释 |
|---|---|
| 内核态/用户态 | CPU 的两种权力档：内核态可以直接指挥硬件，用户态只能申请服务。硬件级安全墙。 |
| RISC-V 的 M/S/U 态 | RISC-V 的三档特权级：M=固件层（机器态）、S=内核层（监管者态）、U=应用层（用户态）。 |
| OpenSBI/SBI | RISC-V 官方 M 态固件+它提供的服务接口。内核请它代办最底层操作（如控制台输出）。 |
| QEMU | 开源机器模拟器：在你电脑里凭空造出一台 RISC-V 电脑，开发 OS 不用买硬件。 |
| 设备树 | 一张「硬件清单表」（树状），内核读它知道这台机器有哪些设备、地址在哪。 |
| Sv39 页表 | RISC-V 的虚拟内存方案：39 位地址空间，虚拟地址经三级表翻译成物理地址。 |
| IPC | 进程间通信：两个程序之间传话的机制。微内核/混合内核架构的主动脉。 |
| capability（能力） | 「令牌式权限」：拿着某令牌才能做某事，无令牌连名字都不知道。比用户名密码式权限更细更安全。 |
| POSIX | UNIX/Linux 软件的「普通话」标准接口。学会了它，Linux 软件就能搬过来重新编译运行。 |
| 宏/微/混合内核 | 内核管多宽：全管（宏）/只管传话（微）/热路径管+故障面外放（混合）。Windows、鸿蒙、macOS 都是混合。 |
| CFS/EDF | 调度算法：CFS=完全公平（按虚运行时间排队）；EDF=最早截止优先（实时任务先做快到期的）。 |
| 伙伴系统/slab | 内核内存管理：伙伴系统按 2 的幂整页分配；slab 把常用尺寸的小对象分池管理。 |
| vDSO | 内核把只读数据映射进应用，读时钟等高频操作不用「陷入」内核，直接读——免敲门。 |
| MMIO/易失 | 内存映射 IO：读写设备的「寄存器地址」就是操作设备；易失=告诉编译器这里别优化别缓存。 |
| DMA | 设备直接读写内存（不经 CPU 搬运），大数据传输的标准姿势。 |
| virtio | QEMU/KVM 的标准化虚拟设备族（磁盘/网卡），写一次驱动通用于所有虚拟机平台。 |
| ELF | Linux 世界的主流可执行文件格式（ Windows 对应 PE/.exe）。 |
| Ability/Stage | 应用模型：Ability=应用的 capability 切片（一个页面/一个后台任务）；Stage=应用声明需求的加载模型。 |
| 软总线 | 鸿蒙首创：把多台设备用软件连成一根「虚拟总线」，设备间像插同一台电脑一样互相调用。 |
| COW | 写时复制：共享时先不复制，谁要改才复制自己那份（省内存）。 |
| LUE/转移() | CN 的拷贝消除：源最后一次使用→自动变移交；显式 转移()=声明此处零拷贝换所有权。 |
| seL4 | 微内核+数学证明安全的业界标杆（形式化验证的圣杯先例）。 |

## 附录 B 三大 OS 对照与吸收总表

| 维度 | Linux | 安卓 | 鸿蒙 | CN-OS 取法 |
