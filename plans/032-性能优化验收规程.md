## 0. 一句话

**任何性能改动 = 基线 + 交替采样 + 指令数口径 + 等价性铁证 + 双编译三平台 + 门禁 + 入账；
缺一项不验收。** 没有数字不叫性能优化，只有数字没有等价性叫危险改动。

---

## 1. 适用范围

适用：

1. 编译器自身性能：宿主 C++ 实现与 v2 CN 实现（加载/词法/语法/语义/IR/优化/代码生成/缓存）；
2. 生成代码与运行时性能：`tests/bench/b1~b8`、stdlib、运行时函数（如 `strlen` 族）；
3. 以性能为目标的缓存、并行化、内存布局、窥孔、寄存器分配、mem2reg 等改动；
4. 性能回退（负优化）与“改了但测不出收益”的改动——同样按本文入账。

不适用：纯文档/纯测试脚本轮。但**采样工具自身必须带 `--selftest`**，且纯脚本轮按
`AGENTS.md` §5 跑自带自测 + L1 静态段。

## 2. 口径（先定口径，再测数字）

### 2.1 三类时钟与可信度排序

| 口径 | 采集方式 | 可信度 | 使用边界 |
|---|---|---|---|
| **指令数** | Linux `perf stat -e instructions`；无 PMU 用 `callgrind` 的 `Ir` | 最高（与调度/负载基本无关） | **收益判定的唯一硬口径** |
| CPU 时间 | `task-clock` / `clock()` / 进程 CPU time | 中（受频率/迁移影响） | 指令数不可得时的次选；须绑核+多轮 |
| 墙钟 | `perf_counter` / `time` | 最低（多会话、I/O、调度全进来） | 只作参考；不得在噪声带内宣称收益 |

硬规则：

- **时钟受扰只认指令数。** 多会话并行、机器负载高、CI 同机混跑时，墙钟差异不得作为收益结论；
  必须改用 `perf instructions` 或 callgrind `Ir` 复核。
- **callgrind 与 perf 不可混比。** callgrind `Ir` 是插桩指令数，绝对值不等于原生指令数；
  A/B 两侧必须同一后端、同一构建、同一命令。跨后端只比“方向/相对变化”，不比绝对值。
- **跨机不比绝对值。** `M1/M2/M5`、墙钟、指令数都带机器/构建类型指纹；报告必须写明
  机器、构建类型（Debug/Release）、平台、编译器版本。
- **噪声带先报告再下结论。** 每侧至少 3 个样本，报告样本表、中位、极差。若改前/改后中位差
  落在两侧样本极差内，判“无可测收益”；项目在 Debug 构建上多次观测到 ≤4% 的负载噪声带
  （#103 实录：三点改造合计约百 ms 级，明确不作收益宣称），因此：
  - 差异 <2%：一律视为无结论，除非指令数同向且超出样本极差；
  - 差异 2%~4%：必须指令数复核 + 交替配对，不得只拿墙钟下结论；
  - 差异 >4%：仍须指令数/等价性证据，不能只凭墙钟。
- **多线程口径分离。** 并行 codegen/opt 测量须先固定 `CN_CODEGEN_THREADS=1` 做单线程归因，
  再用默认线程数做端到端；两者不得混为一张表。

### 2.2 M1/M2/M5 定义（`scripts/bench_self_host.py`·560-a v2 口径）

| 测量点 | 定义 | 用途 |
|---|---|---|
| **M1** | C++ 宿主 `cn build CN语言编译器v2/主.cn -> v2p` 的时间 | 宿主编译 v2 全树的基线 |
| **M2** | v2p（CN 版编译器）编译 v2 全树自身 -> `fix_p`，≥3 次取中位 | CN 版编译器自身速度 |
| **M3** | 汇编 `fix_p -> cn_self.obj` | 汇编器外部成本 |
| **M4** | 链接 `cn_self` | 链接外部成本 |
| **M5** | `cn_self` 再编译 v2 全树 -> `fix_s`，≥3 次取中位 | 自举代际质量 |
| **M6** | `fix_p ≡ fix_s` 逐字节一致 | 固定点/正确性断言 |

读数：

- `M2/M1` = CN 版 vs C++ 版（“性能达 C -O0”口径）；
- `M5/M2` = 自举两代编译器自洽比（固定点成立时 ≈1.00；明显 >1 = 产物质量代际退化）；
- M3/M4 是外部工具成本，不得算进编译器本体收益；
- M6 不成立时，M2/M5 的数字没有验收意义。

### 2.3 冷/热口径（缓存任务强制分离）

| 口径 | 定义 | 环境/操作 |
|---|---|---|
| **冷（cold）** | 首次编译，AST 缓存与程序级缓存均未命中 | `CN_NO_AST_CACHE=1 CN_NO_PROGRAM_CACHE=1`；删除输出；每轮前清缓存 |
| **热（hot）** | 缓存命中：同一输入、同一编译器、同一缓存目录，先预热一轮再测 | 保留默认缓存；预热一轮不计入样本；用 `CN_AST_CACHE_STATS=1` / `CN_PROGRAM_CACHE_STATS=1` 记录命中 |
| **原样（asis）** | 不主动清/不预热，按当前缓存状态 | 只用于复现用户现场，不得用于收益验收 |

硬规则：

1. 缓存类任务（如 #1272 整程序级预编译缓存）**必须同时报告冷/热两组数字**；
2. **热态命中不得冒充门禁收益**：热态省下的是重复编译时间，不是编译器变快；
   门禁/性能验收看冷态或明确标注的热态；
3. 报告必须写清缓存开关、预热轮数、命中统计；缓存未命中时的“收益”一律不认；
4. 冷态测量前删除 `target/` 中相关产物，防“输出已存在”导致空跑；
5. 跨机器/跨用户缓存目录不共享（缓存键含编译器自身身份，但不含机器指纹——报告须注明本机口径）。

## 3. 标准采样流程（改前/改后交替 ≥3 轮）

### 3.1 准备

1. 固定被测对象：同一编译器二进制、同一构建类型（Debug/Release 写明）、同一输入、同一命令行、
   同一工作目录、同一环境变量；
2. 改动前后各**只构建一次**，测量期间不重建、不切换二进制；
3. Linux 上尽量 `taskset -c <核>` 绑核；记录 `load average`、CPU 型号、核数、是否多会话；
4. 清缓存口径按 §2.3；冷态每轮前清，热态先预热；
5. 先跑一次冒烟，确认 `rc=0` 且产物行数/大小在预期范围（防“近乎空产物”假绿）。

### 3.2 交替与轮数

- **交替采集**：A B A B A B……，不是先跑 3 次 A 再跑 3 次 B；交替可抵消机器负载漂移；
- 每侧 **≥3 个有效样本**；样本被中断/超时/产物异常则作废并补跑；
- **取中位**，不取平均；同时保留全部样本入报告；
- 若两侧中位差落在样本极差内，增加轮次或改指令数，不得直接宣称收益；
- 多平台/多构建类型分别成表，不混算。

### 3.3 记录字段（缺一不可）

| 字段 | 示例 |
|---|---|
| 任务号/标题 | #1154 阶段B1 |
| 机器/平台/构建 | ChenChao-PC·linux-x64·Debug |
| 负载命令 | `cn build CN语言编译器v2/主.cn --target linux-x86_64` |
| 缓存口径 | cold / hot（命中统计） |
| 轮数/样本 | A: [..] B: [..]，各 3 轮 |
| 指令数中位 | 48,863,963,725 → 48,185,063,350（-1.39%） |
| CPU/墙钟 | 仅参考，注明是否受扰 |
| 等价性 | asm sha256 / 诊断 stderr / 双编译 / 三平台 |
| 结论 | 收益/负优化/无结论（噪声内） |

### 3.4 工具

- 端到端：`python scripts/bench_self_host.py`（M1/M2/M5）、`python scripts/bench_stdlib.py`（b1~b8）；
- 函数级归因：`python scripts/perf_sample.py --target <平台> --load v2-build --runs 3`
  （见 `plans/033`）；A/B 两侧各跑一次，交替执行；
- 无 PMU/win：`perf_sample.py` 自动降级 callgrind；win 原生只有墙钟，热点走 WSL callgrind 代理，
  代理结果只用于“哪段代码热”，不作为 win 指令数/收益证据。

## 4. 等价性铁证

### 4.1 语义不变类（默认要求）

“性能优化”默认承诺不改语义。必须同时给出：

1. **汇编产物 sha256 逐字节一致**：同目标、同优化级别、同输入、同编译器身份；报告字节数、sha256；
2. **诊断 stderr 逐字节一致**：警告/错误行数、文本全同（若有诊断顺序变化，须逐条解释）；
3. **双编译**：宿主与 v2 两侧都跑；只改一侧时，另一侧产物应不变（或按 §5 成对改）；
4. **可执行产物哈希**（可得时）：v2p/测试产物 md5/sha256 一致；
5. **单测 + 定向 E2E**：见 §6。

范例（#1154 阶段B1）：汇编 44,106,705 字节、sha256 `c2970771...3e24` 改前后一致；
诊断 stderr 351 行警告逐字节一致；单测 1461/1461。

### 4.2 预期产物变化类（窥孔/寄存器分配/布局等）

允许产物变化，但必须证明“变化正是预期的那一类”：

1. 用差分工具过滤**预期删除/新增行**后，其余文本逐字节一致；
2. 报告删除/新增行数、按平台分列、残余未解释行必须为 0 或逐条分类；
3. 同一输入重复编译两次，产物逐字节一致（确定性）；
4. 产物能被目标汇编器/链接器接受（`as` / `aarch64-linux-gnu-as` / `ml64` `rc=0`）；
5. 三后端（win-x64 / linux-x64 / linux-arm64）分别做上述 1~4；
6. 语义面回归：相关 E2E 子集 + 单测；必要时加负测/边界用例。

工具先例：`tests/tools/peephole_artifact_diff.py`（`--selftest` 4 正例 + 1 负例）。
范例（#1279）：linux-x64 -O2 974,946→957,338 行（-17,608）、win-x64 1,156,739→1,134,148
（-22,591）、linux-arm64 1,190,320→1,176,278（-14,042）；过滤被删自搬行后与基线逐字节一致；
两连编一致；三目标汇编器 rc=0。

### 4.3 不接受的“等价”论证

- “看起来一样”“跑一遍没崩”“只在 O2 验过”“只有 linux 验过”；
- 只给摘要哈希不给字节数/命令/输入；
- 预期变化没有过滤器，直接说“差异都是优化”；
- 用热缓存结果证明冷编译收益；
- 用 qemu/模拟器墙钟证明 arm64 指令数收益。

## 5. 双编译与三平台复测

### 5.1 双编译（宿主 + v2）

- 性能改动默认两侧同构落地；只在宿主侧改 = 分叉风险，须呈报并双侧对齐
  （以 `plans/001` 规范为唯一裁决依据）；
- 验证：宿主与 v2 各自编译同一输入，产物/诊断按 §4 对拍；E2E 双通道照跑；
- 缓存/语法/语义类改动必须同时验 v2 自举链（78_v2/79_v2 或等价锚定链）。

### 5.2 三平台

| 平台 | 最低要求 | 备注 |
|---|---|---|
| win-x64 | 宿主/v2 产物行数、汇编器 `ml64 rc=0`、E2E；墙钟仅参考 | 原生无 PMU/callgrind；热点用 WSL callgrind 代理，不作 win 指令数证据 |
| linux-x64 | `perf instructions` + asm sha256/差分 + E2E | 主力指令数口径 |
| linux-arm64 | 原生 arm64：`perf instructions`；无 arm64 真机：qemu 只给墙钟/相对时间 | qemu 下不得宣称指令数收益；产物行数/差分仍须三后端做 |

- 同一改动三平台产物分别比对；不得用 linux-x64 结果替代 win/arm64；
- 平台缺失时，报告写“未测/边界”，不得写“等价/已复测”；
- #1248 / #1279 的教训：性能结论只在 linux-x64 实测时，win/arm64 必须补产物行数与正确性面，
  这是机械要求，不是“有空再说”。

### 5.3 优化级别

- A/B 必须同 `-O0/-O1/-O2` 级别比较；跨级别差异不是收益证据；
- 至少验证 `-O0/-O1/-O2` 三档语义一致（产物可运行、E2E 通过），并记录各档指令数/产物行数；
- `-O3` 当前不收敛（#1255/#1167 实录：16 轮触顶、总时间 75.5s），性能验收默认不把 -O3
  当主口径；若改动触及 -O3，必须单独报告收敛轮数与耗时，不得混入 -O2 结论。

## 6. 门禁义务（性能任务收口清单）

性能类任务收口至少跑：

| 门禁 | 命令 | 要求 |
|---|---|---|
| L1 快速门禁 | `python scripts/gate_quick.py` | 全绿（静态段 + 增量构建 + 全量单测） |
| L2 影响面 | `python scripts/gate_quick.py --l2` | 按写集推导的 E2E 子集全绿（收工面） |
| 定向 E2E | `python tests/e2e/run_e2e.py --filter <族>` | 相关族全绿；负例按预期失败 |
| 双编译 | 宿主 + v2 同测 | 禁单侧/豁免/跳过 |
| 汇编宽度 | `python scripts/check_asm_width.py` | 代码生成/寄存器分配改动必跑 |
| miss 登记 | `python scripts/check_miss_gate.py` | 新增静默默认值=红；先呈报批准再登记 |
| 文件/函数长度 | `python scripts/check_file_length.py` / `check_fn_length.py` | 新增不超红线；>900 行先拆再加 |
| 云全量 | `python scripts/integrate.py` | 触及全量面时走云端 test-then-commit；不直推 develop |

补充：

- 纯脚本/纯文档轮按 `AGENTS.md` §5 走快速通道：跑该脚本 `--selftest` + L1 静态段，
  提交信息附证据（#1011 先例）；
- 缓存类改动必须跑缓存失效矩阵/回归（#1213/#1272/#1273 先例），并报告冷/热两组；
- 性能改动若新增“查表 miss 取默认值”路径，按 #1238 兜底批准制逐条呈报，禁止按类批量批；
- 门禁红不得以“性能收益大”为由放行。

## 7. 负优化与“无结论”入账

1. **负优化如实入账**：改前/改后数字、百分比、影响面、取舍理由、后续任务号；
2. 为正确性/安全/可维护性接受变慢的，标“负优化·已接受”，并登记后续优化任务；
3. 一项指标变好、另一项变差的（如指令数降但墙钟升），两项都写；
4. 测不出收益的，写“无结论（噪声内）/未达可测阈值”，不得写成“优化完成”；
5. 负优化不得被后续提交的“平均/合并口径”掩盖；按提交逐项可追溯。

## 9. 提交信息模板（性能改动）

```text
〔任务号〕标题——指令数 ±x%·汇编逐字节一致

改前/改后（交替 N 轮·口径）:
- instructions 中位: A → B（±x%）（样本: [...]）
- task-clock 中位: ...（是否受扰/是否仅参考）
- 缓存: cold/hot（命中统计）

等价性:
```
