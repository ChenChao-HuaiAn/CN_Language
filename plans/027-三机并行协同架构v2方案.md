# 027 三机并行协同架构 v2 方案（分支即开发·队列即集成）

> **建立**：2026-09-18（第 328-a 轮·单位机 ARM64；用户提出痛点并批准本方案——见 §一）。
> **定位**：三机协同协议 v2 的**方案全文与判定依据**（规则正文=AGENTS.md §8；本表=论证、业界
> 对照、实施与试点记录）。v1 协议（开发锁唯一·231-a/232-a）自此被 v2 取代。
> **规则与方案分工**：AGENTS.md §8=每机每次会话加载的执行规则；本文件=为什么这样设计、
> 用户裁决记录、试点复盘与后续迭代。

## 一、问题诊断（用户痛点与旧模式失败根因）

**用户痛点（2026-09-18）**：
1. 开发锁唯一 ⇒ 每刻只有 1 机产出代码变更，另 2 机最多测试——**浪费 2 台机器**；
2. 测试机发现漏洞只能登记排班、不能当场修——**不够灵活**；
3. 09-15 曾放开三机并行，但公共文件写入总出错，且他机看到错误不主动维护（不在职权范围）。

**09-15 多锁直推失败的三大根因**（lessons 4410·231-a 裁决实录）＋衍生事故：
1. **语义耦合**：写集不相交只防 git 文本冲突，防不住「A 改的接口/语义正是 B 任务的依赖面」；
2. **验证基线漂移**：A 的验证结论锚定的基线被 B 的提交推进后失准（「结果打架」）；
3. **一致性真空**：多锁下没有任何一台机器对全局状态负责，合并口径靠各机自行裁决；
4. 衍生事故：轮次撞号双占（185-a）、rebase 冲突标记入库多日（229-a/233-a）、HANDOFF 指数膨胀
   （lessons 206）、验证轮同信息 30+ 连推（281-a）、plans/021 裁决留档三犯（B5/C21）。

**关键认知**：旧模式的错误不在「并行」，而在「N 机直推同一条共享分支（develop）」——
共享可变状态无隔离。业界几百人并行开发同一仓库（rustc/Chromium/Google）从不靠单锁，
靠三件套：**分支隔离 + 串行受控集成 + 门禁跑在合并结果上**。三大根因各有对应解，
不需要退回单锁：
- 语义耦合 → 门禁在「develop+分支」的**合并结果**上跑（不是分支孤证）；
- 基线漂移 → 集成时强制 rebase 到最新 develop 再验证，结论永远标注 commit；
- 一致性真空 → develop 恒绿恒唯一事实源，分支=隔离实验区，集成=唯一入关口（串行）。

## 三、用户裁决记录（2026-09-18）

1. **缺陷处置权=分级处置**：机制级缺陷（实现 bug·根因唯一·不新增语言语义）当场开分支修、
   修完随证据备案；语义/规范级（语言语义/新关键字/规范缺口/架构决策）先呈报三方案经裁决再修。
2. **跨平台门禁=按风险分层 try-build**：三平台产物相关写集（src/tests/CMake/build/ci.ps1）
   → 三平台 try-build 全绿才集成；纯文档/平台无关脚本 → 本机门禁；另两平台始终集成后验证兜底。
3. **共享文档=随分支走+集成时合并**：开发期文档改动全进分支，集成时随代码串行合并；
   看板保留直推作轻量实时状态。
（方案整体于同日经计划审批流程批准，含六总纲、实施步骤与试点安排。）

## 四、机制细则（与 AGENTS.md §8 同步的摘要）

1. **分支即开发（§8.1）**：分支名 `任务/<机>-<轮次>-<标识>`；推分支=认领（分支名远端唯一=
   天然防撞号——185-a 教训机制化根治）；分支 ≤1 工作日、每日 rebase；看板降为纯信息板。
2. **队列即集成（§8.2）**：`scripts/integrate.py`=develop 唯一入关口——fetch→rebase（冲突自己解·
   禁止 develop 手解）→写集分类→门禁（跑在合并结果上）→push ff-only（CAS 竞争输家自动重试 ≤3）→
   github 镜像补推→通告段广播影响面。
3. **分层验证（§8.3）**：try-build 触发面=src/**、tests/**、CMakeLists.txt、build.ps1、
   scripts/ci.ps1；流程=推分支→通告段点名→另两机在分支上验各自平台→回签→全绿才
   `--try-build-done` 集成；超时 2 小时挂起不降级；集成后验证常设（B8 采样/回归轨/全量门禁）。
4. **缺陷分级（§8.4）**：判定=修复会改变 plans/001 规范条文/新增语法→语义级；其余→机制级；
   模糊按语义级。机制级修复须含 famscan 复跑归零+负测/E2E 转正。
5. **文档随分支（§8.5）**：开发期 plans/025/HANDOFF/更新日志/plans/021/lessons 改动全进分支；
   分区规则保留=合并友好结构保证；直推窄通道=看板+服务轮写面；服务轮同轮单提交。
6. **职权 fix-forward（§8.6）**：「不在职权范围」废除→「一切行为面改动走自己的分支」；
   他机分支问题=通告+可基于其分支开修复分支；develop 红=全员停+破坏者优先修+任何人可 revert。

## 六、试点安排与复盘记录（试点后回填）

- **试点设计**：协议合入后下一轮起，两机各开真实任务分支并行开发一轮（建议家机=清零波次续轮、
  深度机=x64l 侧任务——天然两平台互为 try-build）→各自 integrate.py 集成→本节复盘。
- **复盘面**：集成 push 竞争频率／try-build 应答时长与在线率／rebase 冲突实际发生率／
  服务轮窄通道推送噪音／开发并行度实际提升（对比 v1 同期轮次产出）。
- **回退路径**：协议为纯文档+脚本——回退=恢复旧 §8 文本+删 integrate.py+还原 check_handoff
  校验，零代码风险；回退与否由试点复盘数据呈报用户裁决。
- **✅ 试点复盘回填（509-a·2026-09-20·家机·素材=09-19~20 三天全表实战·develop 328-a→509 轮约 180 轮）**：
  - **① push CAS 竞争频率**：常态日≈每机 1~3 次竞争（重试即过）；**多会话竞速期（09-20 晚·同机 5+ 会话连发）实锤极端形态**——家机 468 九链集成轮连续 8+ 轮 CAS 输家（每轮代价=全量门禁 45min 白跑），push 窗口 <90s 即被抢。**对策已实证**：「集成中」标注+原子循环脚本（merge→push→integrate 全自动·021/025 键级并集+棘轮滚转+看板行压缩）+循环 ≤8 轮最终收敛。**教训级发现**：竞速期窄通道直推与分支集成 push 极易误操作（468-a 实录=标注提交误连分支内容 HEAD:develop 直推·绕过 integrate.py·幸内容门禁已实证全绿·诚实备案）——**协议增补建议=标注/看板直推必须单 commit 分枝（git push gitcode <commit>:develop），禁 HEAD:develop**。
  - **② try-build 应答时长与在线率**：工作时段应答 <2h 达标率高（多轮回签 30min~2h 内到达）；深夜/周末按裁决豁免机制兜底（win+linux 双签·arm64 周末豁免周一补验=运转良好）；**挂起不降级**纪律全程无破例。
  - **③ rebase 冲突实际发生率**：代码/用例面≈0（写集分区纪律有效）；**共享文档 100% 必冲突**（021 案行/025 六要素/coverage_map 矩阵行/看板行——各自演进必然同区），解法定式已成熟：分机节取最新+键级并集（案行/矩阵行）+coverage_map 脚本合并+棘轮自动滚转；HANDOFF.md 旧路径 modify/delete 按 426-a 通告删。
  - **④ 窄通道推送噪音**：同会话多结论合并单推执行良好；竞速期看板行超限（§8.8 上限 4→481-a 后 6）反复触发→「行压缩」入原子循环；采样日志/day 日志双会话并发追加已实测安全（append-only）。
  - **⑤ 开发并行度实际提升**：v1 单锁模型同日 2~3 轮上限；v2 试点期实测**同日 20+ 轮**（09-20 单日 451~509 家机+深度机 448~508 两线·含多会话多开）——吞吐提升约一个数量级；九链积压（429~439）在 48h 内全部收官入 develop。
  - **⑥ 已暴露的协议改进项（呈报用户裁决·非阻塞）**：a) 集成门禁期 CAS 竞争的「白跑 45min」成本——可评估「集成队列锁」（看板通告段已实现软性「集成中」·可升级机械锁）；b) 共享文档冲突自动化（021 键级并集脚本可入 scripts/ 转正）；c) 看板行上限与多开实态匹配（4→6 已随实态调整·后续按需）。
  - **结论**：**v2 协议试点成功·无回退需要**——零打架（语义耦合由门禁在合并结果上拦截·468g/468h 两轮实证）、九链积压消化、并行度一个数量级提升；改进项 ⑥ 全部为增强性质不阻塞现行协议。
