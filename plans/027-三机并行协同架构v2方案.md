## 一、问题诊断（用户痛点与旧模式失败根因）

**用户痛点（2026-09-18）**：
1. 开发锁唯一 ⇒ 每刻只有 1 机产出代码变更，另 2 机最多测试——**浪费 2 台机器**；
2. 测试机发现漏洞只能登记排班、不能当场修——**不够灵活**；
3. 09-15 曾放开三机并行，但公共文件写入总出错，且他机看到错误不主动维护（不在职权范围）。

**09-15 多锁直推失败的三大根因**（lessons 4410·231-a 裁决实录）＋衍生事故：
1. **语义耦合**：写集不相交只防 git 文本冲突，防不住「A 改的接口/语义正是 B 任务的依赖面」；
2. **验证基线漂移**：A 的验证结论锚定的基线被 B 的提交推进后失准（「结果打架」）；
3. **一致性真空**：多锁下没有任何一台机器对全局状态负责，合并口径靠各机自行裁决；
4. 衍生事故：轮次撞号双占（185-a）、rebase 冲突标记入库多日（229-a/233-a）、HANDOFF 指数膨胀
   （lessons 206）、验证轮同信息 30+ 连推（281-a）、plans/021 裁决留档三犯（B5/C21）。

**关键认知**：旧模式的错误不在「并行」，而在「N 机直推同一条共享分支（develop）」——
共享可变状态无隔离。业界几百人并行开发同一仓库（rustc/Chromium/Google）从不靠单锁，
靠三件套：**分支隔离 + 串行受控集成 + 门禁跑在合并结果上**。三大根因各有对应解，
不需要退回单锁：
- 语义耦合 → 门禁在「develop+分支」的**合并结果**上跑（不是分支孤证）；
- 基线漂移 → 集成时强制 rebase 到最新 develop 再验证，结论永远标注 commit；
- 一致性真空 → develop 恒绿恒唯一事实源，分支=隔离实验区，集成=唯一入关口（串行）。

## 三、用户裁决记录（2026-09-18）

1. **缺陷处置权=分级处置**：机制级缺陷（实现 bug·根因唯一·不新增语言语义）当场开分支修、
   修完随证据备案；语义/规范级（语言语义/新关键字/规范缺口/架构决策）先呈报三方案经裁决再修。
2. **跨平台门禁=按风险分层 try-build**：三平台产物相关写集（src/tests/CMake/build/ci.ps1）
   → 三平台 try-build 全绿才集成；纯文档/平台无关脚本 → 本机门禁；另两平台始终集成后验证兜底。
3. **共享文档=随分支走+集成时合并**：开发期文档改动全进分支，集成时随代码串行合并；
   看板保留直推作轻量实时状态。
（方案整体于同日经计划审批流程批准，含六总纲、实施步骤与试点安排。）

## 四、机制细则（与 AGENTS.md §8 同步的摘要）

1. **分支即开发（§8.1）**：分支名 `任务/<机>-<轮次>-<标识>`；推分支=认领（分支名远端唯一=
   天然防撞号——185-a 教训机制化根治）；分支 ≤1 工作日、每日 rebase；看板降为纯信息板。
2. **队列即集成（§8.2）**：`scripts/integrate.py`=develop 唯一入关口——fetch→rebase（冲突自己解·
   禁止 develop 手解）→写集分类→门禁（跑在合并结果上）→push ff-only（CAS 竞争输家自动重试 ≤3）→
   github 镜像补推→通告段广播影响面。
3. **分层验证（§8.3）**：try-build 触发面=src/**、tests/**、CMakeLists.txt、build.ps1、
   scripts/ci.ps1；流程=推分支→通告段点名→另两机在分支上验各自平台→回签→全绿才
   `--try-build-done` 集成；超时 2 小时挂起不降级；集成后验证常设（B8 采样/回归轨/全量门禁）。
4. **缺陷分级（§8.4）**：判定=修复会改变 plans/001 规范条文/新增语法→语义级；其余→机制级；
   模糊按语义级。机制级修复须含 famscan 复跑归零+负测/E2E 转正。
5. **文档随分支（§8.5）**：开发期 plans/025/HANDOFF/更新日志/plans/021/lessons 改动全进分支；
   分区规则保留=合并友好结构保证；直推窄通道=看板+服务轮写面；服务轮同轮单提交。
6. **职权 fix-forward（§8.6）**：「不在职权范围」废除→「一切行为面改动走自己的分支」；
   他机分支问题=通告+可基于其分支开修复分支；develop 红=全员停+破坏者优先修+任何人可 revert。

## 八、v3 裁决记录（异步验收制·581-a·2026-09-21）

**用户原始质询（2026-09-21）**：「怎么什么任务都要别的机器回签？不能家机开发完成，最后其他两个机器测试吗？不通过就让那个机器改呗！没有平台特性限制的任务怎么也要等回签？是不是应该规定：家机全量开发，最后再其他平台验收？参考成熟项目开发经验设计开发流程。」

**两轮侦查要点**（581-a 开工侦查）：① integrate.py 内部本无同步等待——try-build=「快速失败+看板纸面回签+`--try-build-done` 声明」，等待全在脚本外；② 实态=三机 10+ 条已完工链同卡「挂等回签」（家机六链/深度机 546/547/549/550/551/单位机 557/558/559）、547 一链卡 10 条排队链、569 回签被 573 集成架空（回签树≠集成树·白签重签）、单位机周末离线挂等 1~2 天逼出双签豁免机制；③ 试点期回签确有捕获（568 runner 平台硬编码/501 EXTERN 寄存器），但该缺陷面（asm 符号/位宽/平台硬编码）大部分可被本机静态扫描覆盖（check_asm_width 三后端交叉扫描+check_win_asm=交叉编译静态验证·连 Linux 0-day robot 都没有的手段）；④ 纯文档/python 写集本就免签（用户「平台无关也要回签」体感主要来自开发轮几乎必触 src/tests）。

**业界对照（v3 判定依据）**：rustc/bors、Chromium CQ、Google 采用「合并前跨平台验证」的前提是 **7×24 自动化 CI 农场**——等待=全自动几十分钟，人不等机器。本项目跨平台验证执行者=需人开机的 AI 会话，此前提不成立 ⇒ 同步回签必然退化为积压。无自动 CI 的最成功项目=Linux 内核主线，用的正是质询的模式：**直接合入 + 0-day robot 事后扫全部架构 + patch 作者修复义务 + revert 文化**。v3=该模式本土化：开发机门禁绿即集成（零等待）→他机开工时补验收最新 develop→红=验收机当场修（谁的平台谁修）/红灯广播+48h revert 授权→红灯不冻结集成（fix-forward）。回签树≠集成树的结构性浪费随验收对象=集成后真树而消失。

**用户两裁决（2026-09-21·AskUserQuestion）**：① try-build 前置回签处置=**彻底废除，全改异步验收**（否决「降级为自愿预告」与「维持现状」）；② develop 平台红灯处置=**不冻结，广播后继续集成**（否决「冻结集成等回绿」）。

**v3 落地面**：AGENTS.md §8（总纲七条+「任何任务不因等待他机而阻塞收工」+§8.2 步骤 4 删+§8.3 重写+§8.5 窄通道增验收基线登记）、integrate.py（删 try-build 拦截与分类面·--try-build-done/--win-verified 废弃兼容）、check_handoff.py（看板 🧵 验收基线行校验·缺失容忍）、看板三机小节增「🧵 验收基线」行。

**风险明码化（诚实边界·v3 接受的代价）**：
1. **develop 红灯窗口**：他机不在线期平台红灯潜伏（窗口=至该机下次开工）——与 v2 末期 arm64 周末豁免期的既有风险等同，v3 只是把该事实状态推广到全平台并明码化（广播义务+48h revert SLA 约束窗口上限）；
2. **运行级平台缺陷发现滞后**：T44/T27 SIGSEGV/SIGFPE 类静态扫不出，发现时点从他机「被点名的回签」后移至「该机下次开工的补验收」——但 v2 实态下 arm64 运行级验证本就常等 1~2 天，实际滞后增量有限；asm 语法/位宽/符号面由静态补偿前置拦截；
3. **验收积压可能**：他机长期不上线则验收基线持续落后——红灯广播+契约通告持续可见（看板即状态），上线后补验收天然支持批量（一次对最新 tip 全量门禁覆盖全部增量提交）。

**存量挂等链处置（581-a 契约通告）**：v2 末期全部「挂等回签」在飞链（各自本机门禁已绿）随 v3 生效直接按 §8.3「开发轮零等待」集成，他机异步验收兜底；集成序按各机原定序号保持。
