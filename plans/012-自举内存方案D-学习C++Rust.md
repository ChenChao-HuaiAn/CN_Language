# CN 自举编译器内存/性能问题：C++/Rust 成功经验与方案 D 设计

> 2026-08-25 ｜ 目标：自举后的 CN 编译器性能 > C++ 版编译器
> 依据：实测数据（78 前 4 组件 live 峰值 93万~510万、reset 后回落 29~206）+ C++/Rust/GCC/Clang 成熟编译器架构考据

---

## 一、问题本质（实测确认）

CN 自举组件链（词法/语法/语义/IR生成/代码生成）用**字符串行**作为层间中间表示：

```
分词    -> 向量<字符串> "类型|文本|行"       （每 token 一行字符串）
解析    -> 向量<字符串> "缩进+节点"          （每 AST 节点一行字符串）
IR生成  -> 向量<字符串> "调用|符号|参数数|标志|参数码"  （每 IR 指令一行字符串）
代码生成-> 向量<字符串> asm 行               （每汇编行字符串）
```

**每一层都先序列化成字符串，下一层再解析字符串**。实测峰值（单模块活跃 tracked 字符串）：

| 组件 | 源码行 | 活跃字符串峰值 | 对应内存≈ |
|------|--------|--------------|---------|
| 词法分析 | 486 | 93 万 | ~90MB |
| 语法分析 | 1002 | 296 万 | ~300MB |
| 语义分析 | 193 | 39 万 | ~40MB |
| IR生成 | 436 | 510 万 | ~500MB |
| 代码生成 | 1900 | ~500万+(峰值) | 数 GB |

由此：78/79 连续编译 5 组件时，代码生成模块单模块峰值数 GB → 12-16GB 上限仍无法完成。

---

## 二、成熟自举编译器如何做到"快且省内存"（真实机制）

**Rustc（Rust 自举）、GCC（C++ 自举）、Clang/LLVM（C++）的共同架构**：

### 1. Arena / bump 分配器（rustc_arena、LLVM BumpPtrAllocator、GCC ggc）
- 中间表示对象（AST/IR 节点）在 arena 里连续 bump 分配
- **整个编译阶段末尾一次性释放**，无"逐对象 free"的记账开销
- 对应 CN 已有雏形：进程竞技场 __cn_arena_alloc（但只用于编译器一次性进程，未用于组件链中间对象）

### 2. 字符串驻留 / interning（rustc Symbol、LLVM StringPool）
- 标识符/符号名用**整数索引**（Symbol = u32）而非字符串指针
- 字符串内容只在 interner 里存一份，AST/IR/符号表**处处用索引引用，绝不拷贝**
- **这是消除"重复字符串分配"的核心**：相同类型名/符号名不会在每个 AST 行都重新分配

### 3. 结构化中间表示（rustc enum Expr、LLVM Value/Instruction）
- AST/IR 是**结构体/枚举数据**（opcode + 操作数数组），**不是文本行**
- 只有到最后代码生成（AsmPrinter）才格式化为文本
- **绝不在层与层之间反复序列化字符串**（每一层都是结构化对象）

### 4. 借用而非拷贝（&str / StringRef）
- 借用源文本的切片，不分配新字符串

**结论**：C++/Rust 编译器**从不把中间表示序列化成字符串再解析**；它们用结构化数据 + arena + 驻留 + 借用，内存峰值与"每层文本化"无关，只与结构化对象规模线性相关。

---

## 三、CN 自举为何内存高（与上面的差距）

CN 自举组件为了**自举简单**（纯字符串操作、无结构体指针管理）采用了字符串行架构，代价是：

1. **每层全量文本化**：token→AST→IR 各一次完整字符串化 → 百万级字符串分配（实测）
2. **无驻留**：相同类型名（"字符串"、"向量"）在每个 AST 行、IR 行重新分配字符串
3. **无借用**：每层"解析"又重新 create 字符串副本
4. **层间无结构化对象**：只有文本行，无法复用/直接引用的中间对象

**这就是为什么耗时虽快（cache 好、3604 行只要 12s 推演）但内存峰值高**——内存被"文本化冗余"浪费了。

## 四、方案 D 设计（目标：性能 > C++）

### D1：字符串驻留（interning）—— 优先实施，只改运行时，不改组件、不破坏 79 一致性
对标 rustc Symbol / LLVM StringPool：
- 在运行时给 `字符串` 拼接/复制加一个**驻留表**（unordered_map<内容,唯一指针>）
- `字符串复制`/`字符串拼接` 先查驻留表，命中则复用同一块内存（引用计数或同生命周期）
- 效果：AST/IR 行里重复的类型名/符号名只存一份 → 内存峰值大幅下降
- **只改 src/runtime/io_api.cpp**（或 string_api），不动自举组件源码、不影响 79 闭环逐字节产物
- 风险：驻留表生命周期与 reset 交互需设计；字符串可变性（若支持元素写）需禁用或写时复制

### D2：中间表示结构化（重写自举组件）—— 中期，收益最大但影响 79 一致性
对标 rustc enum Expr / LLVM Value：
- IR 行从字符串改为**结构化数组**（如 整64 编码行：opcode码+操作数），消除文本化
- 需同步重写自举组件（IR生成/代码生成）+ C++ 版编译器，影响 79 闭环逐字节一致性
- 工程量大，作为 D1 见效后的延展

### D3：Arena 用于组件链中间对象 —— 与 D1 协同
对标 rustc_arena / LLVM BumpPtrAllocator：
- 复用已有 __cn_arena_alloc，让组件链在 reset 时用 arena 一次性释放
- 与 D1（驻留）配合，进一步降低分配记账与碎片

## 六、关于"性能 > C++"的关键判断（诚实说明）

必须区分两个指标：
- **内存**：D1（驻留）可显著解决——去重重复字符串，代码生成模块峰值有望降到可跑完。
- **耗时**：D1 对耗时帮助有限——CN 自举仍是"每层字符串化再解析"，文本化时间开销仍在。
  要真正让**耗时超过 C++**，必须 D2（结构化中间表示：token/AST/IR 用结构化数据而非字符串行），
  消除逐层文本化。这正是 rustc/LLVM 的做法，也是 C++ 版编译器（src/cn_compiler 用结构化
  IRInstruction）能快的原因。

**结论**：要求"自举性能 > C++"，需同时推进 D1（内存，本轮可做）+ D2（结构化，才耗时超越）。
D1 是前置见效快；D2 是本质工程量大（需同步改 C++ 版与自举组件，影响 79 一致性）。
