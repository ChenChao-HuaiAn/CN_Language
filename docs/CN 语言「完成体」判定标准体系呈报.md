# CN 语言「完成体」判定标准体系呈报

## 一、先直接回答您的三个问题

**1.「什么时候才算没有漏洞？」——诚实的答案：永远不能*证明*没有，只能*收敛*到可声明的成熟度。** 这是数理事实（Dijkstra 定律：测试只能证明缺陷存在，不能证明缺陷不存在）。Rust 编译器至今每年仍修数百个 bug，GCC 走了 40 年也还在修。业界的做法不是「测到没 bug」，而是：①让测试从「点采样」变成「面扫描」；②让每个漏网缺陷自动变成新门禁；③用缺陷发现率下降曲线证明收敛。您现在感到「无穷无尽」，不是因为 CN 特别差，而是因为**当前的发现模式是点状的**（您想到什么、探针扫到什么才测什么），而缺陷分布在一个巨大的面上——点永远采不完面。解法是换武器，不是加耐心。

**2.「测试什么才能说性能大于 C++？」——要测两个维度、且必须有固定基准套件**：①编译器自身性能（编译速度/内存占用）；②生成代码性能（运行速度）。判据、量级、口径见第五节支柱三。

**3.「测试什么才能比肩 Rust 的安全？」——Rust 的安全不是测试出来的，是三层结构**：类型系统设计（借用检查器把 UB 挡在编译期）+ 负测大军（borrowck 约 2000 个 compile-fail 用例证明「错误代码必被拒绝」）+ 运行时兜底（越界即 panic 而非 UB）。比肩的判定=安全属性矩阵逐条对齐，见第五节支柱四。

## 二、Rust 进化史标尺（回答「什么时候」）

| 时间 | Rust 里程碑 | 距项目起点 |
|---|---|---|
| 2006 | 个人项目启动 | 0 |
| 2011 | 编译器自举 | 5 年 |
| 2015 | **1.0（语言稳定性承诺）** | 9 年 |
| 2016~ | crater 全生态回归（在全部 crates.io 代码上做编译验证）、miri 进 CI | 10 年~ |
| 2021 | Android 新组件采用 | 15 年 |
| 2022 | Linux 6.1 内核合入（仅驱动子集，非内核主体） | 16 年（1.0 后 7 年） |
| 2024 | edition 2024，进入 Windows 内核、AWS 等基础设施 | 18 年 |

对照 CN 的位置：**自举已达成（相当于 Rust 2011~2012），但规范仍在变动**（关键字 60→46、冒号后置移除都是最近两周的事）——对应 Rust 的 pre-1.0 语法动荡期。C++ 参照：1983 命名 → 1998 才有第一个 ISO 标准（15 年）。

**诚实的时间判断**：CN 用三机+AI 的强度，走完 Rust 9 年的 1.0 之路不需要 9 年，但也不可能是几周——因为瓶颈不在写代码，而在**验证面的展开量**（下节量化）和**真实世界使用的反馈时间**（Rust 安全声明的可信度一半来自 miri/sanitizer 常年累月的运行）。建议用**里程碑制而非日期制**：每个成熟度等级有硬验收判据，判据不过不算过，这就是您要的「不再我想到什么才做什么」——目标是死的，路径是自动的。

## 三、成熟度阶梯 M1~M8（「完成体」的分解定义）

「完成体」不是一个点，是八个台阶。**每一级都有可复现命令级的验收判据**：

| 等级 | 定义 | 核心验收判据 | CN 现状 |
|---|---|---|---|
| M1 语法完备 | 规范冻结，语言面封闭 | plans/001 每条 EBNF 产生式×{正确/边界/错误}三态用例全覆盖，覆盖率脚本门禁化 | ⬜ 规范在动（A8/关键字裁剪），覆盖率矩阵**不存在** |
| M2 自举闭环 | 编译器编译自己，产物可复现 | 锚定链 fix_p≡fix_s 逐字节 | ✅ **三平台已达成** |
| M3 正确性收敛 | 输入空间大规模采样无逃逸 | fuzzing 持续运行 + 差分对拍零分歧 + 编译器对任意畸形输入不崩溃（T6 类问题绝迹） | ⬜ 无 fuzzing、无差分测试框架；T6/T7 证明此面薄弱 |
| M4 性能达标 | 双维度超过/持平 C++ | 固定基准套件几何平均 + 编译速度对比，回归门禁化 | 🔶 bench_self_host 存在但非门禁、无生成代码性能套件（1.04x 是旧口径单点） |
| M5 安全达标 | 安全属性比肩 Rust | 安全属性矩阵逐条对齐 + Rust 负测移植 + ASan/valgrind 全量常开 | 🔶 编译期安全五阶段完成、探针实证扎实；但矩阵不存在、ASan 只接入单测面 |
| M6 生态可用 | 外部开发者能真正用 | stdlib 完整（迭代器/线程/网络）+ 包管理 + LSP + 文档站 + 错误信息质量 | ⬜ F2-33/34/35 全部未开工（已重评排班） |
| M7 工业交付 | 生产环境敢于部署 | 版本策略+稳定性承诺+大规模真实项目验证+（若进安全关键领域）工具链鉴定 | ⬜ 未启动（Rust 对标=Ferrocene 的 ISO 26262 认证路径） |
| M8 系统能力 | **能写操作系统** | 裸机 target 验证：玩具内核里程碑链（见第六节） | ⬜ 未立项（E1 并发、内联汇编、no_std 层均缺） |

**「能编写各种软件」=M6+M7；「能写 Linux/安卓那样的 OS」=M8 起步、M7 深化**——Linux 主体那样的规模本质是生态+人力问题，语言侧的可验收承诺是「具备写 OS 的全部语言能力并有实物证明」。

## 四、为什么缺陷无穷无尽——诊断

当前缺陷来源结构（从 T1~T10 与 plans/020 各轮归纳）：

1. **规范面无覆盖率证明**——「规范有、实装缺」的缺口（C6/C7/C8/C10 一族连续暴露）是因为没有「规范条文→用例」的映射矩阵，缺口只能靠撞；
2. **输入空间无采样**——畸形输入（嵌套 175 层崩、超码点不拒）只有人想到才测；
3. **双实现×三后端组合面**——9 个组合靠对拍抽查，不是全组合扫描；
4. **安全面是白名单式**——探针想到哪测到哪，没有从「CWE/Rust 安全属性清单」反向穷举。

对应的解法就是把点状设施（现有锚定链/对拍/反证/探针都很扎实，**不推翻、只升级**）织成五张网。

## 五、五大测试支柱（测试什么、多少量、怎么算过）

### 支柱一：规范覆盖率矩阵（M1 的核心，也根治「想到才测」）

- **做什么**：脚本解析 plans/001 全部 EBNF 产生式与语义条文（当前 46 保留字、每类语句/表达式/类型/模块规则），生成「条文编号 × {正例， 边界例， 负例}」矩阵；每格必须有 `tests/e2e/` 用例指针，空格即缺口清单=自动生成的排班队列。
- **量级**：规范约数百条可判定条文 → 预计 **1000~1500 用例**（现 313，缺口约千级但**结构化**——每条缺口直接对应一条规范，不再靠灵感）。
- **怎么算过**：`scripts/check_spec_coverage.py` 报告 100%，纳入 ci.ps1 门禁；规范每次变更（§8.4 契约广播）联动重跑。

### 支柱二：生成式差分测试（CN-Smith，根治「无穷无尽」的主力）

这是 CSmith 2008 年起在 GCC/Clang 上发现数百 bug 的方法，也是**唯一能让测试量超越人力的手段**——一晚上的机器时间等于人数年写用例：

- **做什么**：①写 CN 随机程序生成器（按规范文法生成随机但合法的 CN 程序，控制内存与运行时间上限）；②每个程序在**宿主/v2 双实现×三后端**编译；③全部产物运行比对输出必须一致（差分=立刻定位分歧侧）；④负向生成（随机注入语法/语义错误）验证编译器**永不崩溃、必有诊断**（T6 类问题的机械化歼灭）；⑤已有语料库全量加入轮换池（v2 全树 8.25MB asm 语料、stdlib、全部历史用例）。
- **量级**：持续运行，目标**每日万级程序**采样；不设「多少算够」，以「连续 N 周零新缺陷类别」作为收敛信号。
- **怎么算过**：接入每日/每轮探针轮的角色③职责（三机协议天然有这个档期）；任何逃逸缺陷按现有反证三件套流程根治并自动留负测——这就是「冒一个、关死一类」的收敛闭环。

### 支柱三：性能基准门禁（M4 的判定口径）

- **生成代码性能**：固定基准套件 **20~50 个任务**（排序/图/字符串处理/数值计算/IO 密集/分配密集，Benchmark Game 风格），CN 与 C++ 同算法实现对照，三平台跑；判据=**几何平均 ≥1.0×C++ 且最差单项 ≥0.9×**（不许「平均好看、单项崩盘」），方差报告+统计显著性。
- **编译器自身性能**：用 v2 全树自编译语料（现成语料）跑 `bench_self_host`：自举后 CN 编译器 vs C++ 宿主编译器的时间/内存曲线；判据=**逐文件编译时间与峰值内存全面占优**（这是双目标①的直接口径）。
- **怎么算过**：`scripts/bench_*.py` 进每轮门禁，任何 PR 使基准劣化 >2% 即红灯（Rust 的 rustc-perf 同款机制）；每轮出性能趋势曲线入 plans。

### 支柱四：安全属性矩阵（M5 的判定口径——比肩 Rust 的具体含义）

- **属性清单反向穷举**：从 Rust 保证清单+CWE Top 25 编制 **~50 条安全属性**（UAF/双重释放/泄漏/越界读写/悬垂指针/别名可变性/迭代器失效/数据竞争/整型溢出语义/未初始化读……），每条四件套：CN 机制说明（编译期拦截/运行时兜底/明确不保证）+正例+负例+检测器证据。
- **Rust 负测移植**：borrowck compile-fail 集语义等价移植（约 500~1000 条精选），每条=「Rust 拒绝的错误写法，CN 也必须拒绝」。
- **运行时检测全量常开**：**全部** E2E 用例在 ASan+valgrind 双检下运行零报告（当前只抽查）；F1-30 的 ASan 接入从单测面扩到 E2E 全量。
- **诚实边界（形式化）**：Rust 有 RustBelt/Stacked Borrows 做可信度背书。CN 的最完美长期项=对借用检查器核心做形式化 soundness 论证（CompCert 路线的子集化务实版）；此项列为远期，不阻塞 M5 判定，但必须出现在路线图上——否则「比肩 Rust」在学术界站不住。

### 支柱五：真实世界验证语料（crater 思路，M6/M7 的证据来源）

- **做什么**：拿 CN 写**真实项目**并持续维护：①coreutils 式命令行工具集；②HTTP 服务器；③**玩具内核**（兼作 M8 里程碑）；④编译器自身（已有）。每个项目=持续再生的测试语料+「这语言能不能干活」的实物证据。
- **怎么算过**：每项目有自己 CI（用 CN 编译），纳入总回归。

## 六、「能写操作系统」的分解（M8 里程碑链）

语言层缺口（当前全无）：**no_std 等价层**（不依赖运行时的核心库分层）、**内联汇编**、**链接器脚本/节控制**、**原子操作与内存序**（依赖 E1）、**稳定的裸机 ABI**、中断/异常处理抽象。Rust 的同类能力=core/std 分层+inline asm 稳定化（2021）。

可验收里程碑链（每步实物）：裸机 hello world（无运行时）→ 物理页分配器 → 中断处理 → 任务调度器 → 用户态进程 → **玩具内核跑 shell**。走到最后一步即可声明「语言具备写 OS 的完整能力」（Rust 的 Redox OS 即此定位，2015 至今社区维护、未宣称生产可用——这就是语言能力与生态规模的区别，向您如实呈报预期）。

## 七、与现状的差距汇总与建议落地顺序

现有资产（锚定链/对拍/反证/探针/valgrind/五层所有权模型）**全部保留并升格**为体系内组件；缺口按依赖关系排序：

1. **支柱一（规范覆盖率矩阵）**——立即、收益最大：把「无穷无尽」的第一来源（规范面缺口）变成自动生成的排班队列；纯增量、零语言变更；
2. **支柱二（CN-Smith 生成式差分）**——根治主力，探针轮/验证轮档期即可启动建设；
3. **支柱四之「ASan/valgrind 全量常开」**——F1-30 已接入构建，扩面即可；
4. **支柱三（性能基准门禁）**——需先做 F1-26 Phi 落地（已排程），否则基准失真；
5. **支柱四之安全矩阵+负测移植**——随 C3 收官（波 4/7/8）铺开；
6. **M6 生态三件**（F2-33/34/35，已重评排班）与 **M8 系统能力立项**（E1 并发是前置）。

以上体系的完整落盘建议为 **`plans/026-语言成熟度验收体系.md`**（M1~M8 判据+五支柱实施细则+收敛度量），经您批准后建立，并作为 plans/021 排班队列的上层框架——今后每一轮不再是「想到什么做什么」，而是「体系缺口清单的下一项」。
